# Deterministic Python Development and CI Environments with `uv.lock`

## Summary

Commit the root `uv.lock` and make it the reproducible source of truth for Streamlit's
normal development and CI environments. Preserve the repository's distinct runtime,
test, development, integration, minimum-supported, and latest-compatible dependency
policies through explicit dependency-group selection and narrowly scoped unlocked
workflows.

The repository is already largely ready: it is a uv project, dependency groups are defined
in the root `pyproject.toml`, and Python commands use `uv sync` / `uv run`. Adoption requires
more than adding the lockfile, however: CI must enforce it, cache invalidation must change,
version-mutating workflows must relock, and tests that intentionally install non-locked
versions must prevent `uv run` from restoring the lock.

## Problem

Streamlit currently ignores `uv.lock`, so every fresh environment resolves the newest
versions allowed by broad dependency ranges. This has two undesirable effects:

1. Unrelated PRs can fail when a dependency publishes a breaking release.
2. Developers and CI jobs can use different transitive versions despite starting from the
   same commit.

The current CI virtualenv cache expires daily specifically to approximate a fresh user
install. That provides useful compatibility coverage, but it couples normal PR validation to
upstream release timing. A committed lock should make normal validation deterministic while
moving minimum-version and latest-compatible coverage into explicit jobs.

### Current repository state

- The root project declares `dev`, `test`, and `integration` PEP 735 dependency groups.
  `dev` includes `test`; `integration` also includes `test`.
- `streamlit` is an editable local source, but the root project has
  `dependencies = []`. The source mapping alone does not install it.
- The ignored lock currently resolves successfully and contains 212 packages, 5,336 lines,
  and approximately 944 KiB.
- `uv lock --check` passes. Locked dry-runs pass for the supported Python 3.10-3.14 range
  and for the dev, test, and integration selections used by CI.
- uv resolves all dependency groups into one universal lock and selects a subset when
  syncing. See [uv dependency groups](https://docs.astral.sh/uv/concepts/projects/dependencies/)
  and [project lockfiles](https://docs.astral.sh/uv/concepts/projects/layout/).

### Dependency-group selection is currently not isolated

uv includes the `dev` group by default. As a result, all branches in `make python-init`
currently select development dependencies:

| Requested setup | Current command | Actual selection |
|---|---|---|
| Dev + test | `uv sync --group dev` | Dev |
| Dev only | `uv sync --group dev` | Dev |
| Test only | `uv sync --group test` | Dev (which already includes test) |
| Base | `uv sync` | Dev |
| Integration CI | `uv sync --group integration` | Dev + integration |

The checked-in lock does not prevent distinct environments, but the sync commands must use
`--no-default-groups` and explicit groups. A workspace still has one `.venv`; selecting a
different environment mutates it unless a separate `UV_PROJECT_ENVIRONMENT` is used.

### Pre-existing minimum-dependency test bug

The `py-min-deps-test` job does not currently run against minimum runtime dependencies.
Analysis of develop workflow run `29265918938` showed:

1. `uv pip install -r scripts/assets/min-constraints-gen.txt --force-reinstall`
   downgraded 25 packages.
2. `make python-tests` invoked `uv run pytest`.
3. uv synchronized the project before running pytest and restored all 25 packages to the
   project resolution.

This is expected uv behavior: `uv run` ensures the environment matches the project unless
`--no-sync` / `UV_NO_SYNC=1` is used. See
[uv locking and syncing](https://docs.astral.sh/uv/concepts/projects/sync/).

Two additional issues are hidden by that resync:

- Root `override-dependencies` applies the pandas override while `uv pip install` reads the
  project configuration, so `pandas==1.4.0` is not actually installed.
- Protobuf Python code generated by protoc 26.1 requires a recent protobuf runtime and cannot
  import under the declared minimum `protobuf==3.20`.

Fixing the resync without addressing these issues would make the minimum-dependency job fail
before the test suite starts.

## Goals

- Make normal local and CI installs deterministic for each supported Python/platform marker.
- Preserve separate runtime, test, development, and integration dependency selections.
- Keep minimum-supported and newest-compatible dependency testing meaningful.
- Prevent CI from silently rewriting a stale lock.
- Automatically repair common stale-lock cases through pre-commit and the existing autofix
  workflow.
- Keep direct and transitive dependencies reasonably fresh.
- Preserve the existing 24-hour dependency cooldown unless the team explicitly chooses a
  longer global cooldown.

## Non-goals

- Reproduce operating-system packages, browser binaries, compiler output, or native runtime
  behavior byte-for-byte.
- Lock dependencies for users installing the published Streamlit library. Published metadata
  in `lib/pyproject.toml` remains range-based.
- Replace Dependabot or the minimum-constraints mechanism.
- Maintain multiple checked-in lockfiles for different dependency groups.
- Guarantee simultaneous dev/test/integration virtualenvs in one working tree. Developers who
  need that can set distinct `UV_PROJECT_ENVIRONMENT` paths.

## Proposal

### 1. Commit one universal root lockfile

1. Remove `uv.lock` from `.gitignore`.
2. Regenerate it with the uv version selected for CI and commit it.
3. Mark it as generated in `.gitattributes`:

   ```gitattributes
   uv.lock linguist-generated=true
   ```

4. Add `uv.lock` to CODEOWNERS alongside the Python dependency manifests.
5. Exclude `uv.lock` from `scripts/check_license_headers.py`, as is already done for
   `frontend/yarn.lock`.
6. Exclude only `uv.lock` from the `check-added-large-files` hook. Its current size exceeds
   that hook's default 500 KiB threshold; raising the threshold repository-wide would weaken
   the check for unrelated files. See the
   [pre-commit hook documentation](https://github.com/pre-commit/pre-commit-hooks/blob/main/README.md#check-added-large-files).

The lock remains uv-managed and must not be hand-edited or hand-merged.

### 2. Normalize dependency groups and Make targets

Make the root project dependency model explicit:

```toml
[project]
dependencies = ["streamlit"]

[tool.uv]
default-groups = ["dev"]

[dependency-groups]
test = [
  # test dependencies; `streamlit` comes from project.dependencies
]
dev = [
  { include-group = "test" },
  # development tools
]
integration = [
  { include-group = "test" },
  # integration dependencies
]
```

Listing `dependencies = ["streamlit"]` makes the editable package a real node in the resolved
lock graph so its runtime dependencies from `lib/pyproject.toml` are locked, rather than only
being available through a source mapping. The existing `[tool.uv.sources]` editable entry for
`streamlit` must remain alongside this: `project.dependencies` names the requirement, while
`[tool.uv.sources]` tells uv to satisfy it from the local editable path instead of PyPI.
Streamlit's transitive dependencies resolve identically either way because the local editable
source is used in both cases; the only change is that they now appear in the committed lock
under the `streamlit` node. Validate this during implementation with a no-op `uv lock` diff.

`test` is intentionally the reusable base group, not a second environment that developers
select alongside `dev`. Selecting `dev` already includes all test dependencies. The two
supersets serve different purposes:

| Selected group | Contains |
|---|---|
| `test` | Streamlit and the shared unit/E2E test stack |
| `dev` | `test` plus lint, type-checking, build, and release tools |
| `integration` | `test` plus Snowflake, database, and additional dataframe dependencies |

Users and CI jobs select one final group. Keeping the shared `test` layer avoids duplicating
its dependency list between `dev` and `integration`, while also avoiding unnecessary
development tools in an integration-only environment.

Replace the two boolean dependency selectors with one explicit value, while retaining
Playwright installation as a separate choice:

```make
PYTHON_DEPENDENCY_GROUP ?= dev
```

The supported selections are:

| Environment | Sync command |
|---|---|
| Runtime/base | `uv sync --locked --no-default-groups` |
| Test | `uv sync --locked --no-default-groups --group test` |
| Development | `uv sync --locked --no-default-groups --group dev` |
| Integration | `uv sync --locked --no-default-groups --group integration` |

Expose these through discoverable Make targets (`python-init`, `python-init-test`,
`python-init-integration`) or a validated `PYTHON_DEPENDENCY_GROUP` value. `make all-dev`
continues to select `dev` by default.

Add:

- `make check-python-lock` -> `uv lock --check`
- `make update-python-lock` -> `uv lock --upgrade`

Targeted upgrades remain:

```bash
uv lock --upgrade-package <package>
```

### 3. Pin uv for deterministic automation

Select one tested uv release during implementation and use it in:

- `astral-sh/setup-uv`'s `version` input in the shared CI action.
- The `astral-sh/uv-pre-commit` revision.
- The documented contributor setup baseline.

Keep `[tool.uv].required-version` as the minimum supported contributor version, updated to
the selected release if its lock format or features are required. CI and pre-commit must use
the same exact release even if newer local uv versions remain permitted.

This avoids a strict exact-version requirement for every contributor while keeping the two
automated lock writers consistent. Astral recommends pinning a specific uv version in CI;
see the [uv GitHub Actions guide](https://docs.astral.sh/uv/guides/integration/github/).

### 4. Enforce the lock in normal CI

Add an `enforce_lock` boolean input to `.github/actions/make_init/action.yml`, defaulting to
`true`. Keep that shared action's dependency group explicitly fixed to `dev`: it builds
protobufs and supports jobs that run development tools, so it is not a generic runtime/test
environment constructor. Jobs that need another final selection exact-sync it afterward.

When enabled:

- Run environment creation with locked sync semantics.
- Ensure all `uv run` calls inside the action, including protobuf generation, see
  `UV_LOCKED=1`.
- Fail immediately if either pyproject is inconsistent with `uv.lock`.

When disabled, uv may update the lock. Only workflows whose purpose includes repairing or
regenerating the lock may disable enforcement.

#### Cache behavior

Retain the current virtualenv cache for the initial rollout, but replace its daily key with:

- runner OS and architecture,
- Python version,
- the shared action's explicit `dev` dependency selection, and
- the `uv.lock` hash.

Remove the date and rewrite the obsolete comment describing fresh daily resolution. The
official `setup-uv` cache already includes `uv.lock` in its dependency key.

As a follow-up optimization, benchmark removing the full `.venv` cache and relying only on
uv's package cache. This is lower-risk after deterministic setup has landed.

#### Normal workflow behavior

- Python matrix jobs use locked development dependencies because they run lint, type, and
  tests together.
- Integration setup performs protobuf generation in the development environment, then exact
  syncs the integration selection and runs tests with `UV_NO_SYNC=1` so `uv run` cannot add
  the default development group again.
- E2E, frontend, release, and packaging workflows inherit lock enforcement through the shared
  action.
- Add an explicit `uv lock --check` step to the pre-commit/validation path so stale-lock
  failures are easy to diagnose rather than appearing during a later command.

Use `--locked`, not `--frozen`: `--locked` verifies manifest consistency, while `--frozen`
would use the existing lock without detecting omitted manifest changes.

### 5. Keep the lock synchronized through pre-commit and autofix

Add the official auto-updating hook:

```yaml
- repo: https://github.com/astral-sh/uv-pre-commit
  rev: <selected-uv-version>
  hooks:
    - id: uv-lock
      files: ^(pyproject\.toml|lib/pyproject\.toml|uv\.lock)$
```

The hook updates the lock when a relevant manifest changes. This matches Streamlit's existing
pre-commit behavior: fixable hooks modify files, fail the current commit, and ask the
contributor to review and stage the result. The official hook packages its own pinned uv, so
`enforce-pre-commit.yml` does not need to create the full Streamlit development environment.
See [uv-pre-commit](https://github.com/astral-sh/uv-pre-commit).

Call the shared setup action with `enforce_lock: false` from `autofix.yml`. Otherwise a PR
with a stale lock fails during setup before `make autofix` reaches the uv-lock hook. Autofix
then opens its normal fix PR containing the regenerated lock.

Normal CI, release, and test workflows must not set `enforce_lock: false`.

### 6. Repair minimum-dependency validation

Treat minimum dependency testing as an intentional escape from the project environment:

1. Generate and validate `scripts/assets/min-constraints-gen.txt` as today.
2. Install minimum runtime dependencies with project config disabled so the pandas override
   cannot replace the minimum:

   ```bash
   uv pip install --no-config \
     -r scripts/assets/min-constraints-gen.txt \
     --force-reinstall
   ```

3. Install the local Streamlit package editable with `--no-deps`.
4. Set `UV_NO_SYNC=1` on both the Python test and CLI smoke-test steps.
5. Add a verification step that asserts representative minimum versions before tests, at
   least pandas, protobuf, numpy, pillow, and pyarrow.

#### Protobuf compatibility

The minimum job must generate Python protobuf code compatible with protobuf 3.20. Preferred
implementation:

- Install/download the minimum supported protoc release for this job. The generated Python
  code must import under the protobuf 3.20 runtime, which in practice means a protoc from the
  3.x or early 4.x series; the currently pinned protoc 26.1 emits code that requires a newer
  runtime. Confirm the exact compatible protoc version during implementation.
- Regenerate Python protobuf files with that compiler after minimum dependencies are
  installed.
- Keep frontend protobuf generation in the standard setup path; only Python generated code
  needs to match the minimum runtime for this test.

If using protoc 3.20 is no longer viable, raise the published protobuf lower bound to the
minimum runtime compatible with the current generated code and regenerate
`min-constraints-gen.txt`. Silently allowing pandas or protobuf to float is not acceptable,
because it defeats the purpose of this job.

### 7. Relock version-mutating workflows

`uv.lock` records the editable package's name and version. Any automation that changes
`lib/pyproject.toml` must regenerate the lock before committing or tagging the result.

Update:

- `.github/workflows/nightly.yml`: after `update_version.py` and
  `update_name.py streamlit-nightly`, run unlocked `uv lock` and stage `uv.lock` in the tag
  commit.
- `scripts/create_release_branch.sh`: after `update_version.py`, run `uv lock` before the
  `git commit --all`. This covers normal and patch release-branch workflows.

If the shared setup action exported `UV_LOCKED=1`, these explicit relock commands must unset
it for that command, for example:

```bash
env -u UV_LOCKED uv lock
```

Patching the lock manually from the version scripts is rejected: it couples scripts to uv's
internal lock schema and does not validate the full resolution.

### 8. Preserve newest-compatible dependency coverage

Add `.github/workflows/update-python-lock.yml`, modeled on
`update-browserslist-db.yml` and compliant with the repository workflow rules.

The workflow:

1. Runs weekly and supports manual dry-run dispatch.
2. Checks out `develop` and installs the pinned uv version.
3. Runs `uv lock --upgrade`, using the cooldown configured in `pyproject.toml`.
4. Opens a PR only when `uv.lock` changes.
5. Adds `change:chore`, `impact:internal`, `autofix`, and `never-stale` labels.
6. Uses `actions/github-script` for PR creation and passes dynamic values through environment
   variables in shell steps.
7. Reports whether a lock change and PR were produced in the workflow summary.

The resulting PR runs the complete locked CI suite and becomes the newest-compatible canary.
It is also the bulk update mechanism for transitive dependencies and runtime dependencies
from `lib/pyproject.toml` that are not advanced by the root Dependabot job.

Do not pass a one-off five-day `--exclude-newer` value while `pyproject.toml` declares
`exclude-newer = "24 hours"`; the resulting lock options may disagree with normal lock
checks. Concretely, `uv lock` records the effective `options.exclude-newer` in the lock
header, so a lock produced with a one-off five-day value would fail the next `uv lock --check`
(and therefore every locked CI run) because the header would not match the project-level
`"24 hours"` setting. If a five-day supply-chain delay is desired, change the project setting
globally to `"5 days"` in the same PR. The existing one-day uv cooldown and five-day
Dependabot cooldown are compatible according to the
[uv Dependabot guide](https://docs.astral.sh/uv/guides/integration/dependabot/).

Existing unlocked wheel-install canaries remain valuable:

- `cli-regression.yml` installs the built wheel with fresh resolution.
- `component-template-e2e-tests.yml` tests the built wheel in the external component
  template environment.

### 9. Update Dependabot ownership

Keep the root and `/lib` uv jobs separate for the initial rollout because they intentionally
use different version-range policies:

- Root job: dev/test/integration dependencies with `increase-if-necessary`.
- `/lib` job: published library constraints with widening behavior.

Document the ownership boundary:

- Root direct dependency PRs should update `uv.lock`.
- `/lib` manifest PRs may leave the root lock stale; the `autofix` label repairs it through
  the uv-lock hook.
- The weekly full relock owns bulk transitive and runtime lock freshness.

Batch root minor/patch dependency updates to reduce PR volume; keep majors separate. Observe
the first uv Dependabot runs before increasing the open-PR limit.

GitHub version updates target direct dependencies by default, though uv supports explicitly
allowing indirect dependencies. A weekly batched full relock is preferred over opening a PR
per transitive dependency. See
[Dependabot dependency selection](https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain/manage-your-dependency-security/controlling-dependencies-updated).

The current comment claiming that uv does not support `versioning-strategy: widen` should be
revalidated against GitHub's current schema and updated; current GitHub documentation lists
`widen` for uv.

### 10. Contributor documentation

Update `CONTRIBUTING.md` and generated agent instructions with:

- The committed lock is the source of truth for development and normal CI.
- Environment selection commands for runtime, test, dev, and integration.
- Dependency change workflow: edit/add dependency, run `uv lock`, review, and commit both
  files.
- Targeted and full upgrades.
- Minimum-dependency and latest-compatible test policies.
- Merge conflict recovery:

  ```bash
  git checkout origin/develop -- uv.lock
  uv lock
  ```

  Never hand-merge `uv.lock`.

- A reminder to run `uv lock` after changing the package name or version.

Update `.github/workflows/AGENTS.md` with the new scheduled workflow. Regenerate derived
agent instruction files using the repository's existing generator.

## Rollout Plan

### Phase 1: Deterministic baseline

Land together:

- committed lock and repository-policy exclusions,
- pinned automation uv version,
- explicit dependency-group selection,
- locked shared CI setup and lock-based cache,
- uv-lock pre-commit hook,
- autofix escape hatch,
- nightly/release relocking,
- minimum-dependency resync/pandas/protobuf fixes,
- contributor documentation.

Lock enforcement must not land before the workflows that mutate project metadata are able to
regenerate and commit the lock.

### Phase 2: Dependency freshness automation

Add or enable:

- weekly full-relock PR workflow,
- Dependabot grouping/comment updates,
- monitoring of the first automated update PRs.

This may land in the same PR, but separating it reduces the blast radius of the baseline
adoption.

### Phase 3: Cache simplification (optional)

Benchmark CI with the full `.venv` cache removed. Adopt uv-cache-only setup if CI duration is
acceptable and cache behavior is more reliable.

## Validation Plan

### Lock and environment selection

- `uv lock --check` passes with a clean tree.
- Re-running `uv lock` without upgrades produces no diff, including no cooldown timestamp
  churn.
- Runtime, test, dev, and integration syncs install different expected package subsets.
- Locked dry-runs pass for Python 3.10, 3.11, 3.12, 3.13, and 3.14 on Linux.
- At least one macOS local sync passes to validate the universal markers used by
  contributors.

### CI and pre-commit

- Normal PR CI does not modify `uv.lock`.
- Deliberately changing either pyproject without the lock fails locked CI.
- The uv-lock hook regenerates the lock locally and in pre-commit CI.
- Autofix repairs a stale lock instead of failing during setup.
- The initial lock commit passes the license-header and large-file hooks.
- Cache hits use the same locked versions and invalidate when the lock changes.

### Dependency policy jobs

- Minimum-version assertions prove that the selected packages remain downgraded when pytest
  starts.
- Generated protobuf modules import under the minimum protobuf runtime.
- Integration tests run after the integration-only exact sync without implicit dev resync.
- A manual full-relock dry run either reports no change or produces a valid PR diff.

### Release paths

- A dry-run nightly name/version mutation produces a clean, valid lock and stages it.
- Normal and patch release-branch creation update the lock after the version bump.
- Downstream nightly-tag Python, frontend, E2E, and packaging jobs pass with locked setup.

## Risks and Mitigations

| Risk | Mitigation |
|---|---|
| Lock becomes stale while manifests change | uv-lock pre-commit hook, autofix, and locked CI |
| New upstream releases are no longer caught on arbitrary PRs | Weekly full-relock PR plus unlocked wheel-install canaries |
| Transitives remain pinned indefinitely | Weekly `uv lock --upgrade` |
| `/lib` Dependabot PR cannot update the root lock | Autofix relocks; weekly refresh provides bulk coverage |
| Minimum job silently restores locked versions | `UV_NO_SYNC=1` plus explicit version assertions |
| Pandas override defeats minimum install | `uv pip install --no-config` |
| Minimum protobuf cannot import generated code | Generate with compatible protoc or raise the supported lower bound |
| Large lock fails repository policy checks | Narrow large-file and license-scanner exclusions |
| Version/tag automation creates a stale lock | Explicit relock in nightly and release-branch paths |
| Different uv writers create lock churn | Pin the same uv release in CI and uv-pre-commit |
| One lock cannot resolve future conflicting groups | Declare uv group conflicts only if a real incompatibility appears; use explicit group syncs |

## Alternatives Considered

### Continue resolving fresh dependencies in every CI run

**Pros:** Maximum immediate exposure to upstream releases; no lock maintenance.

**Cons:** Unrelated PRs remain nondeterministic, environments differ between developers and
CI, and transitive breakage is discovered without a focused dependency-update diff.

**Decision:** Rejected. Preserve fresh-resolution coverage in explicit jobs instead.

### Maintain separate lockfiles for dev, test, and integration

**Pros:** Groups could resolve independently if they need incompatible versions.

**Cons:** uv naturally resolves all groups into one universal lock; separate projects would
duplicate metadata and update automation and make cross-environment drift harder to review.

**Decision:** Rejected unless a concrete, irreconcilable dependency conflict appears.

### Collapse the test group into dev

**Pros:** One fewer named dependency group and a simpler model if every environment always
installs the complete development toolchain.

**Cons:** Integration would either duplicate the full test dependency list or include `dev`
and install unrelated lint, type-checking, build, and release tools. It would also remove the
option of a smaller test-only environment.

**Decision:** Rejected. Keep `test` as the shared base for the separate `dev` and
`integration` supersets. Simplify the Make interface so callers choose one group rather than
combining boolean dev/test flags.

### Use only Dependabot for lock freshness

**Pros:** Less custom automation.

**Cons:** Version updates cover direct dependencies by default, `/lib` has separate manifest
ownership, and transitives can remain stale for long periods.

**Decision:** Rejected. Dependabot handles focused direct updates; weekly relock handles the
complete graph.

### Consolidate root and `/lib` Dependabot jobs

**Pros:** A single bot job would always own the root lock.

**Cons:** Root development dependencies and published library constraints intentionally use
different versioning strategies and review labels.

**Decision:** Do not consolidate initially. Revisit if the autofix relock path proves noisy
or unreliable.

### Make pre-commit check-only

**Pros:** No automatic lock mutations.

**Cons:** More manual work and no automated repair path for bot PRs. Streamlit's existing
pre-commit convention already supports reviewed auto-fixes.

**Decision:** Use the official auto-updating uv-lock hook and rely on commit failure/diff
review to surface its changes.

### Patch package name/version directly inside `uv.lock`

**Pros:** Avoids a network resolution in nightly and release automation.

**Cons:** Depends on uv's internal lock schema and can miss other metadata changes.

**Decision:** Rejected. Run a real `uv lock` operation.

## Open Decisions

1. **Selected uv version:** Choose and test one release for CI and uv-pre-commit during
   implementation. Do not assume the current developer-installed version is the target.
2. **Cooldown:** Keep the existing global 24-hour uv cooldown, or change it globally to five
   days to match Dependabot. Do not override it only in the scheduled workflow.
3. **Protobuf lower bound:** Generate min-compatible code in the minimum job, or raise the
   published protobuf minimum. Preferred: preserve 3.20 by generating with a compatible
   protoc (3.x / early 4.x series, not the pinned protoc 26.1) in that job.
4. **Environment command interface:** Separate Make targets versus one validated
   `PYTHON_DEPENDENCY_GROUP` variable. Both must use explicit no-default-group semantics.
5. **Root development Python range:** Optionally restrict lock resolution to the currently
   supported 3.10-3.14 range through the dev project or `tool.uv.environments`; this can
   reduce future-Python resolution churn but requires an update whenever support expands.
