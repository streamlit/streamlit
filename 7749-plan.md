# Plan: Enabling Dynamic Data Updates for st.data_editor

**Issue**: [#7749 - Using st.data_editor with session state, input data "disappears"](https://github.com/streamlit/streamlit/issues/7749)

## Executive Summary

The `st.data_editor` widget currently cannot properly handle dynamic updates to its underlying data structure when used with session state. This causes user edits to "disappear" or require double-input to register changes. This document outlines the root cause analysis and proposes a phased solution to unlock dynamic data updates.

## 1. Problem Statement

### Reproduction Scenario

```python
import streamlit as st
import pandas as pd

if "df" not in st.session_state:
    st.session_state.df = pd.DataFrame({"In": [0, 1, 2], "Out": [0, 0, 0]})

st.session_state.df = st.data_editor(st.session_state.df)
st.session_state.df["Out"] = st.session_state.df["In"] ** 2
st.write(st.session_state.df)
```

### Observed Behavior

1. User inputs a value (e.g., 5) in a cell, presses Enter
2. The input is immediately replaced with the previous value
3. User must input the same value again for it to persist
4. Edits are always "one loop behind" in updating

### Expected Behavior

Each input should immediately:

1. Update the widget's internal state
2. Allow subsequent code to process the updated data
3. Re-render with the correct values (including computed columns)

### Impact

- 83+ upvotes on the issue
- Prevents common data processing workflows
- Forces workarounds that break user experience

## 2. Root Cause Analysis

### The Fundamental Conflict

The issue stems from a **circular dependency** between three systems:

```
┌─────────────────────────────────────────────────────────────────┐
│                        Script Execution                          │
├─────────────────────────────────────────────────────────────────┤
│  1. data_editor(session_state.df)                               │
│     ├─ Widget ID = hash(data + config)  ← ID changes when       │
│     │                                      data changes!         │
│     └─ Returns: df with edits applied                            │
│                                                                  │
│  2. session_state.df["Out"] = ...  ← Modifies the dataframe     │
│                                                                  │
│  3. RERUN triggered                                              │
│     └─ data_editor sees "new" data → new widget ID               │
│        └─ Previous editing state is orphaned                     │
└─────────────────────────────────────────────────────────────────┘
```

### Technical Details

#### 1. Widget ID Computation (Backend)

```python
# lib/streamlit/elements/widgets/data_editor.py:1075-1089
element_id = compute_and_register_element_id(
    "data_editor",
    user_key=key,
    key_as_main_identity=False,  # ← Data IS included in ID!
    dg=self.dg,
    data=arrow_bytes,            # ← Hash of the entire dataframe
    width=width,
    height=height,
    # ... other params
)
```

**Problem**: The `data=arrow_bytes` means ANY change to the dataframe content creates a NEW widget identity.

#### 2. EditingState is Delta-Based

The editing state stores changes as deltas relative to the original data:

```typescript
// frontend/lib/src/components/widgets/DataFrame/hooks/EditingState.ts
class EditingState {
  private editedCells: Map<number, Map<number, GridCell>>  // row → col → cell
  private addedRows: Array<Map<number, GridCell>>
  private deletedRows: number[]
  private readonly numRows: number  // Original row count
}
```

The backend applies these deltas:

```python
# lib/streamlit/elements/widgets/data_editor.py:430-459
def _apply_dataframe_edits(df, data_editor_state, dataframe_schema):
    if data_editor_state.get("edited_rows"):
        _apply_cell_edits(df, data_editor_state["edited_rows"], dataframe_schema)
    if data_editor_state.get("deleted_rows"):
        _apply_row_deletions(df, data_editor_state["deleted_rows"])
    if data_editor_state.get("added_rows"):
        _apply_row_additions(df, data_editor_state["added_rows"], dataframe_schema)
```

**Problem**: Deltas are row-position-based. When the underlying data changes, the positions may no longer be valid.

#### 3. Frontend State Reset Logic

```typescript
// frontend/lib/src/components/widgets/DataFrame/hooks/useWidgetState.ts:119-126
// Reset editing state when originalNumRows changes.
useExecuteWhenChanged(() => {
  editingState.current = new EditingState(originalNumRows)
  setNumRows(editingState.current.getNumRows())
}, [originalNumRows])
```

**Problem**: State is only reset when row count changes, not when data content changes.

### The Race Condition Sequence

```
Timeline:
─────────────────────────────────────────────────────────────────────────────
Run N:
  1. data_editor renders with df (ID: abc123)
  2. User edits cell [0,0] to value "5"
  3. Frontend sends: {edited_rows: {0: {"In": 5}}}
  4. Backend receives edit, stores in widget state for ID abc123

Run N+1 (triggered by edit):
  1. Script reads st.session_state.df (still has old "In" values!)
  2. data_editor called with OLD df → computes same ID abc123
  3. Backend applies edit: df["In"][0] = 5
  4. Script modifies df: df["Out"] = df["In"] ** 2
  5. data_editor RETURNS modified df
  6. session_state.df now has the modified data

Run N+2 (triggered by state update):
  1. Script reads st.session_state.df (has modified data)
  2. data_editor called with NEW df → computes NEW ID xyz789 ← PROBLEM!
  3. Backend sees new widget, no editing state → returns empty edits
  4. User's edit appears to "disappear"
```

## 4. Proposed Solution

### Design Goals

1. **Stable Widget Identity**: Widget ID should remain stable when using a user-provided key
2. **Intelligent State Reconciliation**: Handle data structure changes gracefully
3. **Backward Compatibility**: Existing behavior preserved for keyless usage
4. **Clear Mental Model**: Users understand when/how state persists

### Core Strategy: Key-Based Identity with State Reconciliation

Similar to how `selectbox`, `multiselect`, and `slider` use `key_as_main_identity` with whitelisted parameters, we should:

1. Use the user-provided `key` as the primary identity
2. Only include schema-affecting parameters in the ID computation
3. Implement intelligent reconciliation when data changes

### Proposed Architecture

```
┌─────────────────────────────────────────────────────────────────┐
│ New data_editor Flow                                             │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  Widget ID Computation:                                          │
│  ┌─────────────────────────────────────────────────────────────┐│
│  │ IF key is provided:                                          ││
│  │   key_as_main_identity = {"schema_hash"}                     ││
│  │   ID = hash(element_type, key, schema_hash)                  ││
│  │ ELSE:                                                        ││
│  │   ID = hash(element_type, data, config)  # Current behavior  ││
│  └─────────────────────────────────────────────────────────────┘│
│                                                                  │
│  State Reconciliation:                                           │
│  ┌─────────────────────────────────────────────────────────────┐│
│  │ 1. Check if data changed since last run                      ││
│  │ 2. If schema changed: Clear incompatible edits               ││
│  │ 3. If row count changed: Adjust row indices                  ││
│  │ 4. If data values changed: Mark affected edits as "resolved" ││
│  └─────────────────────────────────────────────────────────────┘│
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

#### B. Schema Hash Function

**Phase 1 Implementation (includes row count):**

```python
def compute_schema_hash(df: pd.DataFrame, arrow_schema: pa.Schema) -> str:
    """Compute a hash of the dataframe schema (structure, not values).

    Phase 1: Includes row count for safety - any row change resets state.
    """
    schema_components = []

    # Include column names and order
    for col in df.columns:
        schema_components.append(str(col))

    # Include column types from Arrow schema
    for field in arrow_schema:
        schema_components.append(f"{field.name}:{field.type}")

    # Include index information
    schema_components.append(f"index:{type(df.index).__name__}")

    # Phase 1: Include row count (row changes = new widget = fresh state)
    schema_components.append(f"num_rows:{len(df)}")

    return calc_md5("".join(schema_components))
```

**Phase 2 Implementation (row count handled separately):**

```python
def compute_schema_hash(df: pd.DataFrame, arrow_schema: pa.Schema) -> str:
    """Compute a hash of column structure only (not row count).

    Phase 2: Row count is tracked separately for smarter reconciliation.
    """
    schema_components = []

    for col in df.columns:
        schema_components.append(str(col))

    for field in arrow_schema:
        schema_components.append(f"{field.name}:{field.type}")

    schema_components.append(f"index:{type(df.index).__name__}")

    # Phase 2: Row count NOT in schema hash - handled by reconciliation logic
    return calc_md5("".join(schema_components))


def get_row_count(df: pd.DataFrame) -> int:
    """Track row count separately for reconciliation decisions."""
    return len(df)
```

#### C. State Reconciliation Logic

```python
@dataclass
class DataEditorReconciler:
    """Reconciles editing state when source data changes."""

    def reconcile(
        self,
        editing_state: EditingState,
        old_data_hash: str | None,
        new_data_hash: str,
        old_row_count: int,
        new_row_count: int,
    ) -> EditingState:
        """
        Reconcile editing state with data changes.

        Returns a new EditingState with invalid edits removed/adjusted.
        """
        if old_data_hash is None:
            # First run, no reconciliation needed
            return editing_state

        if old_data_hash == new_data_hash:
            # Data unchanged, use existing state
            return editing_state

        # Data changed - need to reconcile
        reconciled = EditingState(
            edited_rows={},
            added_rows=editing_state.get("added_rows", []),
            deleted_rows=[],  # Reset deletions - indices may be invalid
        )

        # Filter edited_rows to only include valid row indices
        for row_idx, row_edits in editing_state.get("edited_rows", {}).items():
            if row_idx < new_row_count:
                reconciled["edited_rows"][row_idx] = row_edits

        return reconciled
```

#### F. Summary: What Triggers State Reset vs. Preservation

**Phase 1 (Initial - ✅ Implemented):**

| Change Type | Widget ID | Editing State |
|-------------|-----------|---------------|
| **Cell values only** | Same | **Preserved** ✅ |
| Column added/removed/renamed | Different | Reset |
| Row added | Different | Reset |
| Row removed | Different | Reset |

**Phase 2 (User-Initiated Row Changes):**

| Change Type | Source | Widget ID | Editing State |
|-------------|--------|-----------|---------------|
| **Cell values only** | Any | Same | **Preserved** ✅ |
| Column changed | Any | Different | Reset |
| **Row deleted via UI** | User | Same | **Preserved** ✅ (indices shifted) |
| **Row added via UI** | User | Same | **Preserved** ✅ |
| Row changed externally | External | Same | Reset (can't reconcile) |

**How Phase 2 distinguishes user vs external changes:**

The `EditingState` tracks `deletedRows` and `addedRows` from user actions. We verify:
```
expected_rows = old_rows - len(deletedRows) + len(addedRows)
if new_rows == expected_rows → user-initiated → reconcile
else → external change → reset
```

**Why this works:** When the user deletes/adds rows via the UI, the frontend knows exactly which rows were affected. We can safely shift indices for remaining edits. External changes are unpredictable, so we reset to avoid corrupted state.

### Phase 2: User-Initiated Row Changes - ✅ COMPLETED

**Goal:** Preserve edits when row count changes are caused by user actions through data_editor (deletions/additions). This is the primary use case. External row changes fall back to reset.

#### Key Insight

When row changes originate from the data_editor itself, the `EditingState` already tracks exactly what was deleted/added. We can verify if the new row count matches the expected change:

```
expected_rows = old_rows - len(deletedRows) + len(addedRows)

If new_rows == expected_rows:
    → User-initiated change → Safe to reconcile
Else:
    → External change (or mixed) → Reset to be safe
```

#### 2.1 Backend: Remove Row Count from Schema Hash

```python
def compute_schema_hash(df, arrow_schema):
    """Hash structure only (columns), NOT row count.

    Row count changes are handled by reconciliation logic instead.
    """
    schema_components = []
    schema_components.extend(str(col) for col in df.columns)
    for field in arrow_schema:
        schema_components.append(f"{field.name}:{field.type}")
    schema_components.append(f"index_type:{type(df.index).__name__}")
    # NOTE: num_rows is NOT included - handled by reconciliation
    return calc_md5("|".join(schema_components))
```

#### 2.2 Frontend: Reconciliation Logic

```typescript
// In EditingState.ts or useWidgetState.ts

function canReconcileRowChanges(
  oldRowCount: number,
  newRowCount: number,
  editingState: EditingState
): boolean {
  const deletedCount = editingState.getDeletedRows().length
  const addedCount = editingState.getAddedRows().length
  const expectedNewCount = oldRowCount - deletedCount + addedCount

  // User-initiated change: new count matches expected from edits
  return newRowCount === expectedNewCount
}

function reconcileUserInitiatedChanges(
  editingState: EditingState,
  deletedRows: number[]
): EditingState {
  // 1. Clear deletedRows - they're now reflected in source data
  // 2. Clear addedRows - they're now regular rows in source
  // 3. Adjust editedCells indices for rows below deletions
  // 4. Remove editedCells for deleted rows

  const newEditedCells = new Map()

  for (const [rowIdx, cellEdits] of editingState.editedCells) {
    // Skip edits to deleted rows
    if (deletedRows.includes(rowIdx)) continue

    // Calculate new index (shift down for each deleted row above)
    const deletedAbove = deletedRows.filter(d => d < rowIdx).length
    const newRowIdx = rowIdx - deletedAbove

    newEditedCells.set(newRowIdx, cellEdits)
  }

  return new EditingState(newRowCount, newEditedCells)
}
```

useExecuteWhenChanged(() => {

## 6. Risks and Mitigations

### Risk 1: Breaking Existing Applications

**Concern**: Changing widget ID computation may break apps relying on current behavior.

**Mitigation**:

- Only apply new behavior when user provides explicit `key`
- Keyless `data_editor` retains current behavior
- Add deprecation warning suggesting key usage

### Risk 2: State Reconciliation Conflicts

**Concern**: Reconciled edits may conflict with new data values.

**Mitigation**:

- Clear edits for cells where source data changed
- Preserve only edits that are still "pending" (not yet reflected in source)
- Provide optional `reconciliation_mode` parameter

### Risk 3: Performance Impact

**Concern**: Additional hashing and reconciliation may slow down large dataframes.

**Mitigation**:

- Schema hash is lightweight (column names/types only)
- Data hash can be computed lazily
- Reconciliation is O(n) where n = number of edits (typically small)

### Risk 4: Complex Mental Model

**Concern**: Users may not understand when edits persist vs. are cleared.

**Mitigation**:

- Clear documentation with examples
- Consider adding visual indicator when state is reconciled
- Provide `on_reconcile` callback for advanced users

```python
df = st.session_state.get("df", initial_df)

if "df" not in st.session_state:

st.session_state.df = st.data_editor(st.session_state.df, key="editor")
# Modify in-place instead of creating new column:
st.session_state.df.loc[:, "computed"] = st.session_state.df["value"] * 2
```

## Appendix D: Phase 2 Debugging Findings (Row Operations)

### D.1 Discovered Issues

After implementing Phase 2, we discovered several subtle issues with row operations (deletions/additions):

#### Issue 1: RangeIndex → Index Conversion

**Problem**: When rows are deleted from a DataFrame with RangeIndex, pandas creates a non-contiguous index:

```python
df = pd.DataFrame({"A": [1, 2, 3]}, index=pd.RangeIndex(3))  # index: [0, 1, 2]
df.drop(df.index[1], inplace=True)  # After: index becomes Int64Index([0, 2])
```

This changes the index type, which changes the schema hash, which changes the widget ID!

**Fix Attempted**: Preserve RangeIndex in `_apply_row_deletions`:

```python
def _apply_row_deletions(df, deleted_rows):
    had_range_index = isinstance(df.index, pd.RangeIndex)
    df.drop(df.index[deleted_rows], inplace=True)
    if had_range_index:
        df.reset_index(drop=True, inplace=True)  # Restore RangeIndex
```

#### Issue 2: Widget State Persistence on Backend

**Problem**: The editing state (deletedRows, addedRows, editedRows) is stored in the backend widget state. This state persists across reruns and is re-applied to the dataframe each time.

```
Lifecycle with saved session_state:
1. User deletes row 1 → widget_state = {deleted_rows: [1]}
2. Backend applies deletion → returns df without row 1
3. User saves: session_state.df = modified_df
4. RERUN: data_editor called with modified_df (3 rows instead of 4)
5. Backend reads widget_state → still has {deleted_rows: [1]}
6. Backend applies deleted_rows[1] to the ALREADY-MODIFIED df!
7. Wrong row gets deleted (double-deletion bug)
```

**Root Cause**: The widget state was designed for the scenario where edits are applied to the ORIGINAL source data on each run. When the user saves the modified data back to session_state, the edits become "stale" but are still applied.

#### Issue 3: Frontend State Restoration

**Problem**: On component mount, `useWidgetState` loads the previous editing state from the widget manager:

```typescript
useEffect(() => {
  const initialWidgetValue = widgetMgr.getStringValue(...)
  editingState.current.fromJson(initialWidgetValue, originalColumns)  // ← Restores old state!
}, [])
```

The reconciliation hook (`useExecuteWhenChanged`) doesn't run on first render, so the old deletedRows/addedRows are restored and sent back to the backend.

#### Issue 4: Order of Operations

**Problem**: The backend applies edits in this order:
1. `_apply_cell_edits()` - uses row indices from original data
2. `_apply_row_deletions()` - changes row indices
3. `_apply_row_additions()` - adds at end

Cell edits happen BEFORE deletions are applied. This works on the first run, but on subsequent runs when both the data and the editing state have already been modified, the indices may not align.

### D.2 Key Learnings

1. **Widget State is Backend-Owned**: The editing state JSON (`edited_rows`, `added_rows`, `deleted_rows`) lives on the backend and persists per widget ID. The frontend merely mirrors/updates it.

2. **Deltas are NOT Idempotent for Row Operations**: Cell edits are idempotent (setting cell[0,0] = 5 twice gives the same result). Row deletions are NOT idempotent (deleting row 1 twice deletes two different rows).

3. **Frontend Reconciliation Doesn't Clear Backend State**: Even if the frontend clears its `EditingState`, the backend widget state may still have the old values until the frontend explicitly syncs the cleared state.

4. **`useExecuteWhenChanged` Doesn't Run on First Render**: This is by design, but it means any state loaded in `useEffect` isn't validated by the reconciliation logic.

5. **Initial Widget State Loading Bypasses Reconciliation**: The `useEffect` that loads initial state runs AFTER the component mounts with a fresh `EditingState`, replacing it with potentially stale state.

#### Fix A: Preserve RangeIndex in Backend

### D.5 Alternative Approaches to Consider

#### Approach 1: Clear State After Edits Applied

Instead of trying to reconcile, clear the editing state on the backend AFTER edits are applied to the returned dataframe:

```python
# In data_editor, after _apply_dataframe_edits
_apply_dataframe_edits(data_df, widget_state.value, dataframe_schema)

# Clear the editing state since edits are now "committed"
widget_state.value = {"edited_rows": {}, "added_rows": [], "deleted_rows": []}
```

**Risk**: This would clear ALL edits, even cell edits that the user might want to persist.

#### Approach 2: Track "Applied" vs "Pending" Edits

Add a flag to track which edits have been "committed" to the source data:

```json
{
  "edited_rows": {"0": {"A": 5}},
  "applied_edited_rows": {"0": {"A": 5}},  // These were in previous run
  "added_rows": [],
  "applied_added_rows": [],
  "deleted_rows": [],
  "applied_deleted_rows": [1]  // Row 1 was deleted and committed
}
```

On each run, only apply `*_rows` minus `applied_*_rows`.

**Risk**: Complex state management, potential for drift.

#### Approach 3: Use Data Hash to Detect "Committed" State ❌ FAILED

If the data hash changed AND the editing state has row changes, assume edits were committed:

```python
if data_hash != previous_data_hash and (deleted_rows or added_rows):
    # Data changed with pending row changes → clear row changes
    widget_state.value["deleted_rows"] = []
    widget_state.value["added_rows"] = []
```

**Problem**: The `source_data_hash` is never persisted because the frontend doesn't know about it!
- The widget state JSON comes from the frontend
- Backend modifications to `widget_state.value["source_data_hash"]` are in-memory only
- Each new run, `source_data_hash` is None again

#### Approach 3b: Use Index Bounds Check ❌ FAILED

Check if deletion indices are out of bounds:

```python
if deleted_rows and max(deleted_rows) >= num_rows:
    # Out of bounds → clear stale operations
    editing_state["deleted_rows"] = []
```

**Problem**: Index 1 is still "valid" for a 3-row dataframe!
- Initial: 4 rows, delete index 1 → `deleted_rows = [1]`
- User saves to session_state → now 3 rows
- Next run: `max([1]) = 1 < 3` → doesn't clear!
- Applies deletion to index 1 of the ALREADY-MODIFIED data

#### Approach 4: Frontend-Only Row State

Keep row additions/deletions in frontend-only state that doesn't persist to backend:

```typescript
const [pendingRowChanges, setPendingRowChanges] = useState({ added: [], deleted: [] })
// Only sync to backend for the current render, don't persist
```

**Risk**: Row changes would be lost on page refresh.

### D.6 Fundamental Design Tension

The core tension is:

1. **Edits should persist** across reruns (so user doesn't lose work)
2. **Edits should NOT re-apply** to already-modified data (double-application bug)

For cell edits, these aren't in conflict because cell edits are idempotent.

For row operations, they ARE in conflict because:
- If user deletes row 1 and doesn't save, we want to re-apply the deletion
- If user deletes row 1 and saves, we want to NOT re-apply the deletion

The system has no way to know if the user "saved" the result to session_state!

### D.7 Possible Path Forward

#### Approach 5: Track Original Row Count in Widget State (Recommended)

The frontend's `EditingState` already tracks the original row count. Include it in the widget state JSON:

```json
{
  "original_num_rows": 4,  // Row count when edits were created
  "edited_rows": {"0": {"A": 5}},
  "added_rows": [],
  "deleted_rows": [1]
}
```

Backend detection logic:

```python
original_num_rows = editing_state.get("original_num_rows")
expected_rows = original_num_rows - len(deleted_rows) + len(added_rows)

if original_num_rows is not None and len(data_df) != original_num_rows:
    # Source data row count doesn't match what edits expect
    if len(data_df) == expected_rows:
        # Data matches expected AFTER applying edits → edits were committed
        editing_state["deleted_rows"] = []
        editing_state["added_rows"] = []
```

**Why this works**:
- Initial: 4 rows, delete index 1 → `original_num_rows = 4, deleted_rows = [1]`
- User saves → data now has 3 rows
- Next run: `original_num_rows = 4, len(data_df) = 3`
- Check: `4 != 3` AND `3 == 4 - 1 + 0` → edits were committed → clear!

**Implementation needed**:
1. Frontend: Add `original_num_rows` to `EditingState.toJson()`
2. Backend: Read `original_num_rows` and compare with current row count

### D.8 Key Insight: Timing Problem

The frontend sync CANNOT fix the backend state in time:

```
Timeline:
1. User deletes Bob → frontend sends deleted_rows=[1]
2. Backend stores in widget_state, processes, returns
3. User saves to session_state → RERUN
4. Backend reads widget_state (still has deleted_rows=[1])
5. Backend applies deletion ← TOO LATE TO STOP!
6. Frontend receives new data
7. Frontend reconciles, syncs cleared state
8. (Cleared state only helps the NEXT rerun)
```

The backend MUST be able to detect stale state ON ITS OWN, without relying on frontend sync.

### D.9 Why Frontend Fixes Don't Work Alone

Even with all frontend fixes (don't restore row ops, sync after reconcile), the problem persists because:

1. **Widget state is backend-owned**: The authoritative state lives in the backend session
2. **Frontend sends state, backend reads it**: On each rerun, backend reads stored widget state
3. **Frontend sync is delayed**: Happens AFTER backend processes the current run
4. **Each rerun processes BEFORE frontend can update**: The damage is done

The ONLY fix is backend-side detection of stale row operations.
