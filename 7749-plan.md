# Plan: Enabling Dynamic Data Updates for st.data_editor

**Issue**: [#7749 - Using st.data_editor with session state, input data "disappears"](https://github.com/streamlit/streamlit/issues/7749)

## Executive Summary

The `st.data_editor` widget currently cannot properly handle dynamic updates to its underlying data structure when used with session state. This causes user edits to "disappear" or require double-input to register changes. This document outlines the root cause analysis and proposes a phased solution to unlock dynamic data updates.

## 1. Problem Statement

### Reproduction Scenario

```python
import streamlit as st
import pandas as pd

if "df" not in st.session_state:
    st.session_state.df = pd.DataFrame({"In": [0, 1, 2], "Out": [0, 0, 0]})

st.session_state.df = st.data_editor(st.session_state.df)
st.session_state.df["Out"] = st.session_state.df["In"] ** 2
st.write(st.session_state.df)
```

### Observed Behavior

1. User inputs a value (e.g., 5) in a cell, presses Enter
2. The input is immediately replaced with the previous value
3. User must input the same value again for it to persist
4. Edits are always "one loop behind" in updating

### Expected Behavior

Each input should immediately:

1. Update the widget's internal state
2. Allow subsequent code to process the updated data
3. Re-render with the correct values (including computed columns)

### Impact

- 83+ upvotes on the issue
- Prevents common data processing workflows
- Forces workarounds that break user experience

## 2. Root Cause Analysis

### The Fundamental Conflict

The issue stems from a **circular dependency** between three systems:

```
┌─────────────────────────────────────────────────────────────────┐
│                        Script Execution                          │
├─────────────────────────────────────────────────────────────────┤
│  1. data_editor(session_state.df)                               │
│     ├─ Widget ID = hash(data + config)  ← ID changes when       │
│     │                                      data changes!         │
│     └─ Returns: df with edits applied                            │
│                                                                  │
│  2. session_state.df["Out"] = ...  ← Modifies the dataframe     │
│                                                                  │
│  3. RERUN triggered                                              │
│     └─ data_editor sees "new" data → new widget ID               │
│        └─ Previous editing state is orphaned                     │
└─────────────────────────────────────────────────────────────────┘
```

### Technical Details

#### 1. Widget ID Computation (Backend)

```python
# lib/streamlit/elements/widgets/data_editor.py:1075-1089
element_id = compute_and_register_element_id(
    "data_editor",
    user_key=key,
    key_as_main_identity=False,  # ← Data IS included in ID!
    dg=self.dg,
    data=arrow_bytes,            # ← Hash of the entire dataframe
    width=width,
    height=height,
    # ... other params
)
```

**Problem**: The `data=arrow_bytes` means ANY change to the dataframe content creates a NEW widget identity.

#### 2. EditingState is Delta-Based

The editing state stores changes as deltas relative to the original data:

```typescript
// frontend/lib/src/components/widgets/DataFrame/hooks/EditingState.ts
class EditingState {
  private editedCells: Map<number, Map<number, GridCell>>  // row → col → cell
  private addedRows: Array<Map<number, GridCell>>
  private deletedRows: number[]
  private readonly numRows: number  // Original row count
}
```

The backend applies these deltas:

```python
# lib/streamlit/elements/widgets/data_editor.py:430-459
def _apply_dataframe_edits(df, data_editor_state, dataframe_schema):
    if data_editor_state.get("edited_rows"):
        _apply_cell_edits(df, data_editor_state["edited_rows"], dataframe_schema)
    if data_editor_state.get("deleted_rows"):
        _apply_row_deletions(df, data_editor_state["deleted_rows"])
    if data_editor_state.get("added_rows"):
        _apply_row_additions(df, data_editor_state["added_rows"], dataframe_schema)
```

**Problem**: Deltas are row-position-based. When the underlying data changes, the positions may no longer be valid.

#### 3. Frontend State Reset Logic

```typescript
// frontend/lib/src/components/widgets/DataFrame/hooks/useWidgetState.ts:119-126
// Reset editing state when originalNumRows changes.
useExecuteWhenChanged(() => {
  editingState.current = new EditingState(originalNumRows)
  setNumRows(editingState.current.getNumRows())
}, [originalNumRows])
```

**Problem**: State is only reset when row count changes, not when data content changes.

### The Race Condition Sequence

```
Timeline:
─────────────────────────────────────────────────────────────────────────────
Run N:
  1. data_editor renders with df (ID: abc123)
  2. User edits cell [0,0] to value "5"
  3. Frontend sends: {edited_rows: {0: {"In": 5}}}
  4. Backend receives edit, stores in widget state for ID abc123

Run N+1 (triggered by edit):
  1. Script reads st.session_state.df (still has old "In" values!)
  2. data_editor called with OLD df → computes same ID abc123
  3. Backend applies edit: df["In"][0] = 5
  4. Script modifies df: df["Out"] = df["In"] ** 2
  5. data_editor RETURNS modified df
  6. session_state.df now has the modified data

Run N+2 (triggered by state update):
  1. Script reads st.session_state.df (has modified data)
  2. data_editor called with NEW df → computes NEW ID xyz789 ← PROBLEM!
  3. Backend sees new widget, no editing state → returns empty edits
  4. User's edit appears to "disappear"
```

## 4. Proposed Solution

### Design Goals

1. **Stable Widget Identity**: Widget ID should remain stable when using a user-provided key
2. **Intelligent State Reconciliation**: Handle data structure changes gracefully
3. **Backward Compatibility**: Existing behavior preserved for keyless usage
4. **Clear Mental Model**: Users understand when/how state persists

### Core Strategy: Key-Based Identity with State Reconciliation

Similar to how `selectbox`, `multiselect`, and `slider` use `key_as_main_identity` with whitelisted parameters, we should:

1. Use the user-provided `key` as the primary identity
2. Only include schema-affecting parameters in the ID computation
3. Implement intelligent reconciliation when data changes

### Proposed Architecture

```
┌─────────────────────────────────────────────────────────────────┐
│ New data_editor Flow                                             │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  Widget ID Computation:                                          │
│  ┌─────────────────────────────────────────────────────────────┐│
│  │ IF key is provided:                                          ││
│  │   key_as_main_identity = {"schema_hash"}                     ││
│  │   ID = hash(element_type, key, schema_hash)                  ││
│  │ ELSE:                                                        ││
│  │   ID = hash(element_type, data, config)  # Current behavior  ││
│  └─────────────────────────────────────────────────────────────┘│
│                                                                  │
│  State Reconciliation:                                           │
│  ┌─────────────────────────────────────────────────────────────┐│
│  │ 1. Check if data changed since last run                      ││
│  │ 2. If schema changed: Clear incompatible edits               ││
│  │ 3. If row count changed: Adjust row indices                  ││
│  │ 4. If data values changed: Mark affected edits as "resolved" ││
│  └─────────────────────────────────────────────────────────────┘│
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

#### B. Schema Hash Function

**Phase 1 Implementation (includes row count):**

```python
def compute_schema_hash(df: pd.DataFrame, arrow_schema: pa.Schema) -> str:
    """Compute a hash of the dataframe schema (structure, not values).

    Phase 1: Includes row count for safety - any row change resets state.
    """
    schema_components = []

    # Include column names and order
    for col in df.columns:
        schema_components.append(str(col))

    # Include column types from Arrow schema
    for field in arrow_schema:
        schema_components.append(f"{field.name}:{field.type}")

    # Include index information
    schema_components.append(f"index:{type(df.index).__name__}")

    # Phase 1: Include row count (row changes = new widget = fresh state)
    schema_components.append(f"num_rows:{len(df)}")

    return calc_md5("".join(schema_components))
```

**Phase 2 Implementation (row count handled separately):**

```python
def compute_schema_hash(df: pd.DataFrame, arrow_schema: pa.Schema) -> str:
    """Compute a hash of column structure only (not row count).

    Phase 2: Row count is tracked separately for smarter reconciliation.
    """
    schema_components = []

    for col in df.columns:
        schema_components.append(str(col))

    for field in arrow_schema:
        schema_components.append(f"{field.name}:{field.type}")

    schema_components.append(f"index:{type(df.index).__name__}")

    # Phase 2: Row count NOT in schema hash - handled by reconciliation logic
    return calc_md5("".join(schema_components))


def get_row_count(df: pd.DataFrame) -> int:
    """Track row count separately for reconciliation decisions."""
    return len(df)
```

#### C. State Reconciliation Logic

```python
@dataclass
class DataEditorReconciler:
    """Reconciles editing state when source data changes."""

    def reconcile(
        self,
        editing_state: EditingState,
        old_data_hash: str | None,
        new_data_hash: str,
        old_row_count: int,
        new_row_count: int,
    ) -> EditingState:
        """
        Reconcile editing state with data changes.

        Returns a new EditingState with invalid edits removed/adjusted.
        """
        if old_data_hash is None:
            # First run, no reconciliation needed
            return editing_state

        if old_data_hash == new_data_hash:
            # Data unchanged, use existing state
            return editing_state

        # Data changed - need to reconcile
        reconciled = EditingState(
            edited_rows={},
            added_rows=editing_state.get("added_rows", []),
            deleted_rows=[],  # Reset deletions - indices may be invalid
        )

        # Filter edited_rows to only include valid row indices
        for row_idx, row_edits in editing_state.get("edited_rows", {}).items():
            if row_idx < new_row_count:
                reconciled["edited_rows"][row_idx] = row_edits

        return reconciled
```

#### D. Frontend State Management Updates

**Leveraging Existing `Quiver.hash`**

The frontend already has a hash computation in `Quiver.ts`:

```typescript
// frontend/lib/src/dataframes/Quiver.ts:225-240
public get hash(): string {
  const valuesToHash = [
    this.dimensions.numColumns,
    this.dimensions.numDataColumns,
    this.dimensions.numDataRows,
    this.dimensions.numIndexColumns,
    this.dimensions.numHeaderRows,
    this.dimensions.numRows,
    this._num_bytes,        // ← Changes when data content changes!
    this._columnNames,
  ]
  return hashString(valuesToHash.join("-"))
}
```

This hash is useful because:

- `_num_bytes` changes when ANY data value changes (not just structure)
- Already computed on the frontend
- More comprehensive than just `originalNumRows`

**Enhanced useWidgetState hook:**

```typescript
// useWidgetState.ts - Enhanced state reset logic

interface UseWidgetStateParams {
  element: ArrowProto
  widgetMgr: WidgetStateManager | undefined
  fragmentId?: string
  originalNumRows: number
  originalColumns: BaseColumn[]
  dataHash: string  // Use Quiver.hash from the data prop
}

// Reconcile editing state when data changes
//
// KEY INSIGHT: We don't need to check if user provided a key!
// The component lifecycle handles it:
//   - No key → Widget ID changes → Component REMOUNTS → Fresh state from constructor
//   - Has key → Widget ID stable → Component UPDATES → This hook triggers, we reconcile
//
// This hook only runs on UPDATES (not first render), so if we're here,
// it means the component persisted (user provided key) and data changed.
useExecuteWhenChanged(() => {
  // Data or structure changed while component persisted
  // → Reconcile to preserve valid edits
  const previousState = editingState.current.toJson(originalColumns)
  editingState.current = new EditingState(originalNumRows)
  editingState.current.reconcileFrom(previousState, originalColumns)
  setNumRows(editingState.current.getNumRows())
}, [originalNumRows, dataHash])  // Triggers on row count OR data content changes
```

#### F. Summary: What Triggers State Reset vs. Preservation

**Phase 1 (Initial):**

| Change Type | Widget ID | Editing State |
|-------------|-----------|---------------|
| **Cell values only** | Same | **Preserved** ✅ |
| Column added/removed/renamed | Different | Reset |
| Row added | Different | Reset |
| Row removed | Different | Reset |

**Phase 2 (With Row Addition Support):**

| Change Type | Widget ID | Editing State |
|-------------|-----------|---------------|
| **Cell values only** | Same | **Preserved** ✅ |
| Column added/removed/renamed | Different | Reset |
| **Row added** | Same | **Preserved** ✅ (edits to original rows) |
| Row removed | Same | Reset (unsafe to keep) |

**Why row removals still reset:** The editing state uses positional indices (`edited_rows: {1: {...}}`). If rows are removed, we can't safely determine which rows were deleted, so positions may be invalid.

**Why row additions can be preserved:** If rows are only added (not removed), we assume they're appended at the end. Edits to rows 0..N-1 remain valid since those positions haven't shifted.

```python
class DataEditorReconciler:
    def reconcile(self, editing_state, old_row_count, new_row_count):
        if new_row_count >= old_row_count:
            # Rows added (assume at end) → keep edits within original range
            return self._filter_edits_in_range(editing_state, old_row_count)
        else:
            # Rows removed → can't safely determine which, reset
            return self._create_empty_state()

    def _filter_edits_in_range(self, state, max_row):
        """Keep only edits for rows that existed before additions."""
        filtered = {
            "edited_rows": {
                k: v for k, v in state["edited_rows"].items()
                if int(k) < max_row
            },
            "added_rows": state.get("added_rows", []),
            "deleted_rows": [r for r in state.get("deleted_rows", []) if r < max_row],
        }
        return filtered
```

## 6. Risks and Mitigations

### Risk 1: Breaking Existing Applications

**Concern**: Changing widget ID computation may break apps relying on current behavior.

**Mitigation**:

- Only apply new behavior when user provides explicit `key`
- Keyless `data_editor` retains current behavior
- Add deprecation warning suggesting key usage

### Risk 2: State Reconciliation Conflicts

**Concern**: Reconciled edits may conflict with new data values.

**Mitigation**:

- Clear edits for cells where source data changed
- Preserve only edits that are still "pending" (not yet reflected in source)
- Provide optional `reconciliation_mode` parameter

### Risk 3: Performance Impact

**Concern**: Additional hashing and reconciliation may slow down large dataframes.

**Mitigation**:

- Schema hash is lightweight (column names/types only)
- Data hash can be computed lazily
- Reconciliation is O(n) where n = number of edits (typically small)

### Risk 4: Complex Mental Model

**Concern**: Users may not understand when edits persist vs. are cleared.

**Mitigation**:

- Clear documentation with examples
- Consider adding visual indicator when state is reconciled
- Provide `on_reconcile` callback for advanced users

    assert app.get_cell_value(0, 0) == "5"
    assert app.get_cell_value(1, 0) == "10"

## 8. Open Questions

### Q1: Should reconciliation be opt-in or opt-out?

**Options**:

- A) Always on when key is provided (simpler, may surprise users)
- B) New parameter: `persist_edits=True` (explicit, more control)
- C) Infer from usage pattern (complex)

**Recommendation**: Option A with clear documentation

### Q2: How to handle edits to cells that were modified externally?

**Options**:

- A) Clear the edit (external change wins)
- B) Keep the edit (user edit wins)
- C) Let user decide via callback

**Recommendation**: Option A with optional callback for advanced use cases

### Q3: Should we track edit provenance?

**Context**: Knowing which edits came from user vs. script could help reconciliation.

**Options**:

- A) Add timestamp/source to each edit
- B) Keep simple delta model

**Recommendation**: Start with B, add A in future if needed

### Q4: How to handle the case where user provides key but also modifies data programmatically?

**Example**:

```python
df = st.session_state.get("df", initial_df)
df = st.data_editor(df, key="editor")
df["computed"] = df["value"] * 2  # This creates a new df!
st.session_state.df = df
```

**Concern**: The assignment `st.session_state.df = df` creates a new dataframe object.

**Recommendation**: Document that users should not reassign session state in this pattern. Instead:

```python
if "df" not in st.session_state:
    st.session_state.df = initial_df
st.session_state.df = st.data_editor(st.session_state.df, key="editor")
# Modify in-place instead of creating new column:
st.session_state.df.loc[:, "computed"] = st.session_state.df["value"] * 2
```

## Appendix A: Alternative Approaches Considered

### A1: Use Row IDs Instead of Indices

**Idea**: Track edits by unique row identifiers instead of positional indices.

**Pros**:

- More robust to row reordering
- Better for databases with primary keys

**Cons**:

- Requires user to specify ID column
- Doesn't work for all dataframes
- Significant API change

**Decision**: Not pursuing for initial implementation; could be future enhancement.

### A2: Full Snapshot Storage

**Idea**: Store complete edited dataframe instead of deltas.

**Pros**:

- Simpler reconciliation
- No index mapping issues

**Cons**:

- Much larger state storage
- Performance issues for large dataframes
- Harder to show what changed

**Decision**: Not pursuing; current delta model is more efficient.

### A3: Virtual DOM-style Diffing

**Idea**: Diff old and new data to intelligently merge edits.

**Pros**:

- Most accurate reconciliation
- Handles complex changes

**Cons**:

- Computationally expensive
- Complex implementation
- May produce unexpected results

**Decision**: Not pursuing for initial implementation; too complex.
